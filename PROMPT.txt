用 Preact 写一个本地待办事项应用。

主界面：
- 顶部一个输入框，回车新增待办（自动 trim 空字符串，纯空白的输入忽略）
- 输入框右边一个"高级添加"按钮，弹出浮层可以设置：截止日期、分类、优先级、提醒时间、重复规则
- 中间是待办列表，每条显示：勾选框（点击切换完成状态）、标题、分类小色块、优先级标识、截止日期、剩余天数
- 列表上方有筛选和排序条：按分类筛选、按优先级筛选、按完成状态筛选、按截止日期/创建时间/优先级排序
- 底部状态栏：今日到期未完成数、本周剩余可做数、最近一次完成的时间

每条待办的详情页（点开进入）：
- 标题、描述（多行）、分类、优先级、截止日期、提醒时间、重复规则、创建时间、完成时间
- 子任务列表（每条子任务有自己的勾选状态，主任务完成状态根据子任务自动联动——子任务全完成主任务自动完成，主任务勾选完成所有子任务自动勾选）
- 备注历史（用户改了什么改了时间，附加备注也行）
- 附件链接（多个）

重复规则的实现：
- 支持每天/每周/每月/每年/自定义天数（比如每 3 天）
- 每周可以选星期几（多选）
- 每月可以选几号（1-31，超过当月天数的按当月最后一天）
- 重复任务完成时自动按规则创建下一次的任务（截止日期按规则往后推）
- 重复任务有"修改本次/修改全部/修改未来"的区分

数据存 localStorage（任务列表 + 分类字典 + 用户设置），刷新不丢。导入导出 JSON 备份。

提醒时间到了要弹浏览器原生通知（用 Notification API，先请求权限），不在线时错过的提醒下次打开时一并提示（展示一个"未送达提醒"列表）。

边界：用户创建 1000 条待办不能卡（虚拟列表）；截止日期已经过去的待办要有过期样式（红色标识+按过期天数排序优先）；用户改分类时所有该分类的待办要联动更新（颜色和名称）；用户从筛选状态切回全部时筛选条件要保留（不能丢）。

至少 3 个文件：列表组件、详情组件、状态管理分开。

实际部署里还会涉及这些点：任务的截止日期有"剩余 0 天"显示（今天到期）、"过期 X 天"显示（红色）、"X 天后到期"显示。优先级用颜色（红黄蓝或者 emoji 高/中/低）。筛选器多选时是 OR 关系（满足任一即显示）。拖拽排序时实时计算新位置（不是放下才更新）。子任务编辑有独立的弹窗（不在主弹窗里堆）。提醒弹窗能在系统设置里关（用户主动关掉就不再请求权限）。任务被删除能在最近删除里恢复（保留 7 天）。搜索按 F 键聚焦。

补段用户场景：用户每天有几十条待办（工作+生活混在一起），按分类（工作/学习/生活/其他）管理。每天早上他打开应用看今天到期的（按优先级排），挑最重要的先做。做完勾掉会消失（默认折叠已完成）。晚上他看本周完成情况统计。

他有几个特殊需求：每周一上午要做"周计划"，用"重复规则"自动建周计划任务（每周一重复）。每周三晚上要给妈妈打电话（每周三 20:00 提醒）。周末去超市（每周六 10:00 提醒）。这些都用重复规则。子任务用得不多，但偶尔有"准备周报"这种主任务，下面有"汇总本周数据""写文字总结""发给领导"几个子任务。

提醒系统边界：用户开了浏览器但没开这个应用 tab 时，浏览器原生通知触发不了（不是 PWA 限制）。所以要 SSE 长连接或者定时 poll 后端——但用户没要求后端，所以用 Notification API 在 tab 内 setInterval 弹通知（这是妥协方案）。多个提醒同时到排队弹（不要堆叠）。

实际工作流里还会有这些场景。一条待办任务的状态走"待办-进行中-已完成-已取消-已归档"五态，加上"已删除"软删除态。"待办"用户点开始按钮或者勾第一个子任务自动切到"进行中"。"进行中"可以再次回到"待办"（暂停）或者完成/取消。"已完成"任务在 30 天后自动归档到归档列表（不再出现在主列表），归档前 3 天给用户推"任务 X 即将归档"通知。"已取消"任务不归档（永久在列表里但有"已取消"灰色样式）方便用户回看。状态之间的转换有时间窗口限制——超过截止日期 7 天的"待办"任务不能再"进行中"（要选"已完成"或"已取消"），超过截止日期 30 天的"进行中"任务自动转"已逾期"状态（不同于"已取消"），提示用户处理。

多角色视图：项目里有三种角色——管理员（项目所有者，能邀请/移除协作者、设置项目级的截止日期策略、删除整个项目）、普通协作者（能创建/编辑/完成自己和他人的任务，前提是任务被指派给"所有人"或者被指派给自己）、只读访客（被邀请观察项目进度，能看到所有任务和评论但不能改任何字段）。访客看到的列表里不含"草稿"状态的任务（草稿对其他角色可见但不算"正式"任务）。管理员在设置里能给不同分类设置不同权限——比如"个人事务"分类只有创建者本人能看，"家庭事务"分类所有家庭成员都能看，"工作事务"分类只有被邀请的成员能看。被指派的任务会有"被指派人"字段，被指派人之外的人看不到这个任务的详情（只能在列表里看到标题预览）。

时间与配额：用户每月初有 200 次"任务操作"配额（创建/编辑/删除/状态变更都算一次操作），配额用完后进入只读模式（只能勾完成不能再创建新任务，月底最后一天 23:59 重置配额）。免费版最多 200 条待办（超出提示升级），订阅版无限制（用户在设置里勾"已订阅"标志）。每个任务有"最后编辑"时间戳——超过 90 天没编辑的任务被标记为"沉睡"（半透明显示），超过 365 天没编辑自动移到"沉睡"分类。重复任务在创建后第 30 次重复时给用户推"该重复任务已运行 30 次，是否继续"询问。

并发与数据一致性：用户在两个 tab 同时编辑同一个任务时（都用 localStorage 存），通过 storage 事件和 lastEditedAt 时间戳判断——后编辑的会覆盖先编辑的，但会提示"任务已在另一标签页被修改于 X 时间，你正在覆盖它"。多用户协作者场景下（虽然没有真后端，但 mock 数据模拟 3 个用户在编辑），一个用户改任务状态时其他用户 5 秒内收到同步（用 BroadcastChannel API 在同浏览器多 tab 间同步）。删除任务时（带子任务），子任务按策略处理——"级联删除"（连子任务一起删掉）、"转为独立任务"（保留子任务但解除父子关系，父任务字段置空）、"转移到回收站"（父子都在回收站 30 天后真删）。状态变更会触发"活动时间线"——任务的创建、状态切换、子任务勾选、备注添加、文件附件操作都按时间正序记录，每个事件有操作人昵称、时间戳、变更前/后值。导入 JSON 时检测任务 ID 是否冲突，冲突策略是"保留本地版本生成新 ID"或"用导入版本覆盖本地"，让用户选。导入文件带 exportedAt 时间和 schemaVersion 版本号。
